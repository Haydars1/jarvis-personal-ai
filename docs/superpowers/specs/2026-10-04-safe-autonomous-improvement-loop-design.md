# JARVIS Safe Autonomous Improvement Loop — Design Spec

Date: 2026-10-04
Status: Written-spec review pending
Parent spec: `docs/superpowers/specs/2026-10-03-capability-fabric-v2-design.md`
Branch: `feature/capability-fabric-v2`

## 1. Goal

Allow JARVIS to turn trusted learning evidence and verified repository/tool discoveries into small, low-risk improvements on a feature branch without waiting for repeated micro-prompts, while keeping production, `main`, secrets, paid actions, destructive operations, and high-risk vehicle writes outside the autonomous boundary.

The loop exists to satisfy the product rule: after each safe development cycle, JARVIS should evaluate the result, identify the next useful safe improvement, implement it, test it, and continue until it reaches a gated boundary or has no verified next action.

## 2. Inputs

The loop may consume:

- verified Capability Fabric sources and capability gaps;
- YT Öğretisi development candidates with source/timestamp provenance;
- failing tests and regression evidence;
- capability health/degraded states;
- code-graph dependency information;
- user-approved project goals and constraints;
- safe backlog items generated by prior cycles.

A social post, screenshot caption, unverified README claim, or model suggestion alone is insufficient evidence for autonomous code changes.

## 3. Allowed autonomous changes

Only on a non-production feature/integration branch:

- additive backend code and tests;
- adapter manifests and capability metadata;
- read-only analysis paths;
- UI/status/reporting improvements that do not weaken security;
- test fixtures;
- documentation;
- source/provenance capture;
- compatibility-preserving refactors with passing tests;
- bounded native/iOS changes after the relevant project can be built and verified in CI or Xcode validation.

Every change must be reversible through normal Git history.

## 4. Gated changes

The loop must stop and surface a proposal instead of executing when the next action includes any of the following:

- merge to `main`;
- production deployment;
- creation, rotation, deletion, or exposure of secrets;
- paid API/account purchase or any monetary charge;
- destructive data/schema/filesystem action without a safe reversible migration path;
- account permission escalation;
- publishing externally on behalf of the user;
- high-risk vehicle/ECU write or coding action;
- disabling emissions-control systems or generating executable defeat patches;
- execution of a third-party tool that has not passed the Capability Fabric security/execution gate.

## 5. Cycle

```text
observe current evidence
 -> select one bounded candidate
 -> confirm it is inside autonomous policy
 -> define acceptance test
 -> write failing test where applicable
 -> implement minimal change
 -> run targeted tests
 -> run regression/health checks
 -> record evidence + commit
 -> reassess remaining gaps
 -> continue with next bounded safe candidate
```

A cycle cannot mark itself complete from prose. Completion requires concrete evidence such as tests, build output, or deterministic verification artifacts.

## 6. Candidate scoring

Candidates are prioritized using:

1. user value / blocked workflow;
2. evidence strength;
3. regression risk;
4. implementation size;
5. dependency availability;
6. testability;
7. reversibility.

Prefer the smallest change that unlocks a measurable capability. Do not chase raw repository count.

## 7. Branch policy

- Autonomous edits occur only on an explicitly created feature or integration branch.
- The loop never force-pushes shared branches.
- Each independently verifiable change gets its own commit.
- `main` is read as a baseline and remains unchanged until a separate merge proposal is accepted.
- `feature/learning-engine` is treated as a source branch for controlled convergence, not overwritten wholesale.

## 8. Evidence ledger

Each cycle records:

- cycle ID;
- triggering evidence/source;
- affected specialist agent/capability;
- files changed;
- tests/builds executed;
- pass/fail result;
- commit SHA;
- remaining risk/gaps;
- next candidate;
- reason for stopping when gated.

This ledger feeds the Capability Dashboard and weekly JARVIS status summary.

## 9. Failure behavior

If a change fails tests:

- do not claim completion;
- diagnose within the same bounded scope;
- fix and rerun when safe;
- if the failure requires a gated action, stop that candidate and record it as blocked;
- do not bypass failing checks merely to progress the loop.

If no trustworthy next candidate exists, the loop stops with `no_verified_next_action` instead of inventing work.

## 10. YT Öğretisi integration

YT Öğretisi may generate development candidates, but automatic implementation requires all of:

- source provenance retained;
- discovered repo/tool identity verified;
- capability gap confirmed against current JARVIS state;
- safety policy permits the change;
- bounded acceptance test can be defined;
- no production/secret/paid/destructive/high-risk vehicle gate is crossed.

Educational ECU material can improve analysis, visualization, file metadata, diffing, checksum verification, diagnostics interpretation, and safe workflow guidance. It must not automatically turn emissions-bypass knowledge into executable patches.

## 11. Acceptance criteria

1. A low-risk candidate can be selected and implemented on a feature branch without another micro-command.
2. The cycle records a failing-then-passing test or equivalent deterministic verification where applicable.
3. A successful cycle creates a commit with evidence.
4. A subsequent safe candidate can be selected automatically from remaining gaps.
5. A candidate requiring production deploy stops as a proposal.
6. A candidate requiring secret mutation stops as a proposal.
7. A candidate requiring paid API usage stops before incurring cost.
8. A high-risk vehicle write never executes through this loop.
9. Third-party code cannot enter the loop's execution path before Capability Fabric approval.
10. The UI/status output distinguishes `implemented_on_feature_branch`, `verified`, `blocked_by_gate`, and `proposed_for_merge`.

## 12. Design decision

Chosen model: **autonomous inside a reversible, testable feature-branch sandbox; explicit human gate at irreversible/external boundaries**.

This preserves the user's desired continuous improvement behavior without turning branch-local experimentation into silent production or device actions.
